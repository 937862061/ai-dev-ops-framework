# P0-P2 落地指南

按 [分阶段建设流程](phase-gated-construction.md) 执行并记录阶段状态。P0、P1、P2 之间均有强制确认停点；本文定义每阶段的内容和验收。

## P0：设计确认与最小入口

先与开发者确认下列内容，记录在目标项目的体系设计或 `AGENTS.md` 中，而不是靠 AI 私有推断：

1. 覆盖范围：开发、缺陷排查、接口调整、报表、数据修复、线上运维中哪些纳入体系。
2. 项目级 skill 的维护源、知识库根目录、目录层级及版本管理方式；目录职责按 [知识库目录规划](knowledge-directory-layout.md) 确认，包括开发过程计划统一存放在 `plan/`。
3. 权威来源优先级：通常是业务术语/外部契约、项目知识库、代码与表结构、运行日志；目标项目可按实际调整。
4. 业务概念不清、文档冲突、跨模块、状态流转及高风险操作时，AI 与开发者各自的确认责任。
5. 首次 AI 开发导览的触发范围和本地完成状态的隔离方式。

完成 P0 时，至少落地根 `AGENTS.md`、`ai-knowledge/ai-development-onboarding.md` 与已确认的 `ai-knowledge/` 目录树（名称可调整，但入口、目录职责与实际路径必须一致）。后续相关任务必须先查询本地导览完成记录；仅当前本地 AI 工具和本地开发者没有该项目的匹配记录时，才展示导览并等待确认后开始目标项目事实检索。

**P0 验收**：新 AI 工具仅凭根入口能找到导览、项目 skill 源和知识库；首次导览的禁止事项与本地状态隔离都被明确写出；`system/`、`PRD/`、`plan/` 与 `ops/` 的职责边界已确定；`plan/ai-dev-ops-plan.md` 已记录 P0 决策、待确认项和下一阶段的事实盘点范围。

## P1：项目知识资产

开发者确认导览和 P0 后，基于目标项目实际资料建立或补齐知识库。先按 [知识库目录规划](knowledge-directory-layout.md) 创建或整理目录；按渐进式披露组织：入口文件描述地图和加载策略，具体知识按域/模块拆分，不要求在一个文件堆满所有细节。

必须按 [详细系统文档规范](detailed-system-documentation.md) 完成事实盘点和文档。至少覆盖全量模块清单、关键业务域、主数据表、关键字段和枚举、主要同步/异步链路、外部系统与运维入口；每项都给出可复核的类、方法、Mapper/XML、表、配置或消息锚点。没有证据的内容必须标为待确认，不能写成结论。

P1 的最低资产如下；可按项目调整名称或粒度，但不能省略其职责。

| 资产 | 固定归属 | 最低内容 | 使用方式 |
|---|---|---|
| 架构总览 | `system/architecture.md` | 技术栈、模块依赖、代码入口、配置/外部集成边界 | 首次定位时读取 |
| 术语词典（L1） | `system/glossary.md` | 系统唯一语义、关联代码实体、易混淆点 | 按需求关键词检索 |
| 域/模块逻辑（L2） | `system/flows/`（按主题分子文件夹） | 入口、主流程、边界、外部契约引用 | 仅读取相关主题 |
| 数据字典（L3） | `system/data-dictionary.md` | 关键表字段、枚举全集、状态流转、统计口径 | 按表名/枚举检索，并与实际代码核对 |
| 反模式记录 | `system/anti-patterns.md` | AI 或协作中已证实的错误理解、正确做法、预防措施 | 按关键词/业务域检索 |
| 已知问题清单 | `system/known-issues.md` | 未解决的业务/数据/遗留问题及状态 | 仅在开发者要求分析问题时读取 |
| 原始需求与外部契约 | `PRD/` | 需求原文、签署约定、外部报文/接口契约 | 仅在需求溯源或外部对接时读取 |
| 运维手册 | `ops/` | 环境、巡检、日志、数据修复前置核对、发布回滚 | 运维任务按需读取 |

至少为关键业务域、关键状态机和高风险数据链路提供真实内容。每条知识应标注可追溯的代码、表、接口或外部契约锚点；不确定的内容应标为待确认，不得填入猜测。

**P1 验收**：系统架构位于 `system/architecture.md`，不存在根目录的重复架构事实；模块清单覆盖全部可执行模块且每项有职责/依赖/入口锚点；每个关键业务域都有入口→服务→数据访问→表/消息/外部调用的主链路；数据字典覆盖所有主链路触达的关键表、状态字段和枚举全集；外部集成、定时/MQ/异步消费与运维入口可定位；能用实际关键词定位到核心概念、实际入口和关键字段/枚举；知识库存在按需检索路径；已知问题与 AI 反模式有明确分工；所有关键事实可追溯或标注待确认。

## P2：项目 skill 与跨工具接入

在 `.agents/skills/` 创建三个与项目绑定的 skill；名称可带项目名前缀，但职责必须清晰、互不重复：

| skill | 职责 |
|---|---|
| `<project>-knowledge` | 首次导览、知识地图与加载矩阵、禁止猜测、概念确认清单、事实定位和知识保鲜 |
| `<project>-dev-spec` | 从现有工程与团队约定提炼的分层、命名、事务、异常、数据库、测试与交付规范 |
| `<project>-ops` | 运维/线上排查、SQL 数据修复、巡检、发布回滚的入口和授权边界 |

根 `AGENTS.md` 必须：

1. 指向项目级 skill 的维护源，并要求目标 AI 工具发现自身的项目 skill 路径后同步、链接或回退直读。
2. 根据任务类型要求加载 knowledge、dev-spec、ops；数据修复同时属于知识和运维任务。
3. 把首次导览放在所有开发、排查、运维类事实检索之前。
4. 要求完成改动后检查知识库是否应同步更新，并要求报告未执行的验证。

**P2 验收**：三个 skill 均有有效 frontmatter、描述能区分触发场景、内容引用目标项目真实知识路径；knowledge skill 的加载矩阵能分别定位架构、领域链路、数据字典、PRD、计划与运维文档；`AGENTS.md` 与 skill 的首次导览和阶段停点规则没有冲突；在另一 AI 工具没有项目 skill 同步能力时，仍能按根入口回退读取维护源。

## P3：真实需求试点（可选）

选择一个真实且有代表性的需求（建议跨模块或涉及状态流转），验证 AI 是否在编码前加载 knowledge、检索术语/字段、输出必要的概念确认清单，最后同步知识库。记录实际发现的流程缺口，仅将被证实的问题回填 skill 或反模式记录。

## P4：固化与推广（可选）

将知识保鲜纳入交付检查，在重大重构或固定周期人工核对知识库与代码/表结构；将经过试点验证的蓝图推广到其他项目。不要要求所有项目使用相同技术栈、文件名或审批流程。
