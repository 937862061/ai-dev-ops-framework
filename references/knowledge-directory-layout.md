# 知识库目录规划

本规范用于 P0 设计和 P1 落地。它定义目录职责，不替代目标项目事实；目标项目可以调整文件名或领域文档粒度，但不得让同一类事实分散到多个无明确边界的位置。

```text
ai-knowledge/
├── readme.md                         # 知识库入口、地图、加载策略与维护说明
├── ai-development-onboarding.md      # 首次 AI 开发导览正文
├── ai-dev-ops-design.md              # 体系设计、角色与职责边界
├── PRD/                              # 原始业务需求、签署约定、外部契约
├── plan/                             # 开发过程产生的计划文档
│   ├── ai-dev-ops-plan.md            # P0-P4 计划、验收与实施状态
│   └── <feature-or-topic>-plan.md    # 需求实施、调研或验证计划
├── system/                           # 当前系统的业务与技术事实
│   ├── architecture.md               # 技术栈、模块依赖、代码入口、配置/集成边界
│   ├── glossary.md                   # L1：系统术语、唯一语义、易混淆点
│   ├── data-dictionary.md            # L3：表字段、枚举全集、状态流转、统计口径
│   ├── anti-patterns.md              # 已证实的 AI/协作错误、正确做法、预防措施
│   ├── known-issues.md               # 未解决业务、数据或遗留问题
│   └── flows/                        # L2：主要流程统一收纳于此（按主题分子文件夹）
│       └── <domain>/                 #     领域/主链路主题文件夹
│           └── <domain-or-module>.md #     入口、流程、边界与契约引用
└── ops/                              # 运行操作知识
    ├── inspection.md                 # 巡检与健康检查
    ├── sql-runbook.md                # 排查/数据修复前置核对与经审查 SQL
    └── release-rollback.md           # 发布、回滚与停止条件
```

## 归属规则

| 目录 | 放入内容 | 不应放入内容 |
|---|---|---|
| 根 `ai-knowledge/` | 导航、首次导览、体系设计 | 具体系统架构、术语、表字段、领域流程、过程计划、运维步骤 |
| `system/` | 系统架构、领域流程、术语、数据字典、状态机、反模式、已知问题 | 原始需求全文、生产操作步骤 |
| `PRD/` | 原始需求、评审结论、签署约定、第三方报文/接口契约 | 对当前代码实际行为的未经核对结论 |
| `plan/` | 开发过程中产生的实施计划、调研计划、验证计划及其执行状态 | 已证实的系统事实、原始需求全文、生产操作 runbook |
| `ops/` | 环境说明、巡检、日志检索、数据修复前置检查、发布回滚 | 未经授权的生产操作、业务术语的唯一解释 |

## 强制规则

1. 系统架构必须位于 `ai-knowledge/system/architecture.md`（或语言等价且在 `system/` 下的唯一文件），不得在根目录保留另一份架构事实。
2. `PRD/` 是需求与契约来源，不自动等同于当前实现；涉及实现行为时，必须以 `system/` 文档和代码事实交叉核对。
3. `system/` 根只保留**整体性文档**（architecture / glossary / data-dictionary / anti-patterns / known-issues）；**所有主要流程统一收纳在 `system/flows/` 下按主题分子文件夹**（如 `flows/insurance-application/`、`flows/report/`、`flows/permission/`、`flows/h5/`），每个主要流程可能有多个文件；同一主题只保留一个明确主入口，并由 `readme.md` 建立索引。
4. **单次需求产生的设计文档不单独留存**：只在对应系统逻辑文档（system/ 子文件夹主题文档）中补充主流程/字段/接口变更，避免按单次需求堆叠零散文档；确需保留的过程性计划写入 `plan/`。
5. 开发过程中产生的计划文档必须写入 `plan/`；计划结束后，把已证实的架构、术语、流程或运维结论回填到 `system/` 或 `ops/`，计划本身不能成为唯一事实来源。
6. `ops/` 中涉及数据修复或生产操作时，必须链接实际授权、前置检查、回退方案和停止条件；不能因为文档存在就视为已获执行授权。
7. 调整目录或文件名后，必须同时更新根入口、所有 skill 引用和 Markdown 链接，避免产生失效路径或重复事实。
